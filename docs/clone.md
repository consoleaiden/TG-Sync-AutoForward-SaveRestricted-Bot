# 频道克隆：起点选择、进度记录与断点续传

把任意频道/群组（公开或私有、含话题）的历史消息完整搬到目标频道，支持
指定起点、**指定消息 ID 区间**、实时进度、随时暂停、崩溃后自动续传，
跑完自动转入**持续监听**，克隆记录**永久保留**。

> 内部仍复用原来的 `sync` 任务类型（`tasks.type='sync'`），因此老的
> `/sync` 命令、`message_map` 映射表和已有数据库完全兼容，升级不需要迁移
> 数据，只自动补列。

---

## 1. 交互方式：按钮菜单（推荐）

`/start` 或 `/menu` 打开主菜单，全程点按钮：

```
🤖 TG 克隆助手
├─ 📥 新建克隆任务
│    ① 发源频道链接（或 @用户名）
│    ② 选目标：当前会话 / 发目标频道链接
│    ③ 选起点：从头 / 从指定消息 ID / 从指定时间 / 继续上次进度
│    ④ 选模式：复制 / 转发
│    ⑤ 确认 → 开始（默认跑完转持续监听）
├─ 👁 新建持续监听        （同一套向导，少了「起点」一步）
├─ 📋 克隆任务列表        （含已完成，记录永久保留；🛰 = 持续监听中）
├─ 📡 监听任务列表        （含克隆任务转来的持续监听，标注来源任务号）
├─ 💾 备份数据库
├─ ⚙️ 限流设置
└─ ❓ 命令与说明
```

向导状态保存在内存，15 分钟无操作自动失效；**已创建的任务不受影响**，
随时可从「克隆任务列表」继续。只有三类内容需要手打：源链接、消息 ID、时间。

### 命令速查

| 命令 | 作用 |
| --- | --- |
| `/kl <链接>` | 克隆该频道**全部**消息到本群，完成后自动持续监听 |
| `/kl 100-1100 <链接>` | 只克隆消息 ID 区间（**含两端**） |
| `/kljx <链接>` | 继续克隆：从上次游标补到最新，已克隆过的不重复 |
| `/jt <链接>` | 只监听新消息，不补历史 |
| `/kllb` | 克隆任务列表（含已完成） |
| `/jtlb` | 监听任务列表 |
| `/chapd` | 转发一条频道消息到本群，识别频道名 / @用户名 / ID / 链接 |
| `/help` | 全部命令与功能对照 |

区间写法支持 `100-1100`、`100~1100`、`100—1100`、`100到1100`、`100至1100`；
区间放在链接前后都可以（`parse_clone_args` 先把区间抠出来，剩下的整段当链接）。

兼容旧用法仍然可用：

```
/clone [链接]                          # 等同于点「新建克隆任务」
/sync <链接> [--forward] [--from-id N] [--from-time 2024-01-31[T12:30]]
/syncrestrictedmsg <链接>
/monitor <链接> [--forward]            # 等价 /jt
/list
```

## 2. 克隆起点与终点

起点四种语义，终点默认是**源的最新一条**（正向 最早 → 最新）；用 `/kl A-B` 时终点
是消息 B：

| 起点 / 终点 | 菜单 | 命令 | 内部实现 |
| --- | --- | --- | --- |
| 从头开始 | ⏮ 从头开始 | 默认 | `offset_id=0` |
| 从指定消息 ID | 🔢 从指定消息 ID | `--from-id 1234` | `offset_id = 1234 - 1`（**含** 1234 这条） |
| 从指定时间 | 🕒 从指定时间 | `--from-time 2024-01-31` | 先按时间定位边界消息 ID，再 `offset_id=边界` |
| 继续上次 | ▶️ 继续上次进度 | 点任务里的「继续」/ `/kljx` | 用 `last_synced_msg_id` 作 `offset_id` |
| **到指定消息为止** | — | `/kl 100-1100 <链接>` | `end_msg_id=1100` → `max_id = 1101`（**含** 1100 这条） |

时间格式支持 `2024-01-31`、`2024-01-31 12:30`、`2024/01/31`、`20240131`、
`2024-01-31T12:30`、10 位 unix 时间戳。

> **续传优先**：只要任务的 `last_synced_msg_id > 0`，本次运行一律从游标继续，
> 起点设置不再生效 —— 避免「暂停后又把整个频道克隆一遍」。
> `/kljx` 还会把 `end_msg_id` 清零，否则补不到最新。

## 3. 进度记录

`tasks` 表一行就是一个任务，同时是它的进度快照：

| 列 | 含义 |
| --- | --- |
| `source_chat_id` / `source_topic_id` | 被克隆的源（含话题） |
| `target_chat_id` / `target_topic_id` | 接收目标 |
| `source_title` / `target_title` | 人类可读名称（菜单展示用，避免反复解析） |
| `start_msg_id` / `start_date` | 用户选择的起点（仅首次生效） |
| `last_synced_msg_id` | **克隆游标**：已处理到的源消息 ID |
| `total_count` | 待处理总量（服务端 `count`，非估算） |
| `done_count` / `fail_count` / `skip_count` | 成功 / 失败 / 跳过条数 |
| `notify_chat_id` / `notify_msg_id` | 进度消息位置（原地刷新，不刷屏） |
| `last_error` / `finished_at` | 最近错误 / 完成时间 |

`message_map` 逐条记录 `源消息 ID → 目标消息 ID`，可用于核对是否有重复或遗漏。

进度刷新：每成功转发 `clone.progress_notify_every` 条（默认 50）**编辑同一条
消息**：

```
📥 克隆任务 #12
进度: ▰▰▰▰▰▱▱▱▱▱  45.2%  (4,521/10,000)
游标: msg_id=48213 · 速率 1.2 条/秒
成功 4,500 · 失败 12 · 跳过 9
已用 1h02m · 剩余约 1h15m
```

## 4. 断点续传

三层保障：

1. **每处理完一个转发单元就落盘**（`last_synced_msg_id` + 计数，单行 UPDATE）。
   进程被 kill / 容器重启 / OOM 最多丢当前这一条，不会重头再来。
2. **手动暂停**：点「⏸ 暂停」→ 取消任务 → 状态 `paused`，游标保留。
3. **自动续传**：进程重启后，`status='running'` 的克隆任务会从游标继续
   （`clone.auto_resume: true`）。关掉则置为 `paused`，等手工点「继续」。

续传是**幂等**的：从 `last_synced_msg_id` 之后严格继续，不会重复发送已有内容。

## 5. 跑完之后：持续监听

克隆任务 `completed` 之后默认**不结束使命**：`syncer.on_complete` 会回调
`_on_clone_completed` → `_ensure_follow_monitor`，为同一个「源 → 目标」建一个
`monitor` 任务接管后续新消息，并通过 `parent_id` 反向指回克隆任务。

```
克隆任务 #12  completed   ──follow──▶  监听任务 #18  running
   🛰 持续监听: 开启（监听任务 #18）        （来自克隆任务 #12）
```

- **全局开关**：`clone.follow_after_finish: false` 可关掉这个自动行为；
- **单任务开关**：任务详情里的 `🛰 持续监听: 开启（监听任务 #N）` / `⏹ 关闭`，
  对应按钮 `follow:<id>`（`_toggle_follow`）；
- 关闭只是把对应监听任务置为 `paused` 并清掉 `follow` 标记，**记录与已转发计数都保留**，
  再点一次即恢复；

## 6. 记录永久保留

`completed` 不会再让任务从列表消失：

| 动作 | 效果 |
| --- | --- |
| 克隆跑到末尾 | `status='completed'`，仍在「克隆任务列表」里，带 ✅ 与完成时间 |
| 点「🗑 删除」 | `status='deleted'`（**软删除**），列表看不到，但游标 / `message_map` 仍在库里 |
| 误删想找回 | 直接把 `tasks.status` 改回 `paused`，任务立刻回到列表 |
| 想接着补新消息 | 详情页「🔁 继续补新消息」或 `/kljx <链接>` |
| `/kljx` 已无新消息 | 回复「已是最新」并保持 `completed`，不会空跑 |

列表排序为 `running → paused → failed → 其它（含 completed）`，
`get_tasks_for_list(db, CLONE_TASK_TYPES, 20)` 一次取 20 条。

---

## 7. 大频道不再撑爆内存

旧实现会先把整频道消息全读进内存再逐条转发，几万条就危险。现在按
`clone.batch_size`（默认 200）**流式分批**：

- 边拉边转，内存占用恒定；
- 相册不会被切到两批（`core.clone_plan.split_album_tail` 保证整组进入同一批），
  只有「单组图片数 > batch_size」这种极端情况才硬切；
- 服务消息与空消息（无文本无媒体）计入 `skip_count` 并推进游标，不会卡住。

## 8. 配置

```yaml
clone:
  auto_resume: true          # 重启后自动从断点继续
  batch_size: 200            # 每批拉取条数
  progress_notify_every: 50  # 每 N 条刷新一次进度
  follow_after_finish: true  # 克隆跑完自动转持续监听
```

升级到本版本后首次启动会自动给 `tasks` 表补齐新增列（`PRAGMA table_info`
比对后 `ALTER TABLE ADD COLUMN`，只增不改，老数据保留），本轮新增
`end_msg_id`、`follow`、`follow_task_id`、`parent_id`。

## 9. 常见问题

**Q：点了「继续」但没有任何反应？**
看日志有没有 `克隆任务 #N 已从游标 X 继续`。若源已不可读（UserBot 被踢、
频道转为私有），任务会标记 `failed` 并在 `last_error` 里写明原因，游标保留，
修好权限后可继续。

**Q：克隆完成了，但列表里还想看到它？**
能在。完成的任务状态是 `completed`，仍留在「克隆任务列表」；只有你点删除才会
以 `deleted` 软删除消失，数据仍在库里。

**Q：`/kljx` 会重复克隆吗？**
不会。它按「源（含话题）→ 目标」找最新一条克隆记录，把状态改回 `running`
（保留游标、清空 `end_msg_id`）后从 `last_synced_msg_id` 之后继续；
`message_map` 里已有映射的消息不会再发一次。

**Q：怎么知道某个频道该用哪个 ID？**
先 `/chapd`，再把该频道任意一条消息**转发**到本群，机器人回你频道名、
@用户名、ID 和可直接复制的 `/kl` / `/kljx` / `/jt` 命令。

**Q：目标频道收不到消息？**
先把 Bot 加为目标频道管理员（需要发消息权限）。菜单在选目标时会用
`bot.get_entity` 做一次可达性校验。

**Q：进度条百分比和源里显示的总数对不上？**
`total_count` 是服务端按「游标之后（并受 `end_msg_id` 上界限制）」统计的条数
（含服务消息），实际转发会略少，`skip_count` 会把这些差额显露出来。

**Q：能不能只克隆某个话题？**
可以。发带话题的链接（`https://t.me/c/123456/3/962`）即可，`source_topic_id`
会记录在任务里。

**Q：克隆到一半想改目标？**
不支持改已有任务的目标。建议删掉任务，用「继续上次进度」以外的方式新建一个
（游标是按任务记录的，新任务会从你选的起点开始）。
