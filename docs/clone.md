# 频道克隆：起点选择、进度记录与断点续传

把任意频道/群组（公开或私有、含话题）的历史消息完整搬到目标频道，支持
指定起点、**指定消息 ID 区间**、实时进度、随时暂停、崩溃后自动续传，
跑完自动转入**持续监听**，克隆记录**永久保留**。

> 内部仍复用原来的 `sync` 任务类型（`tasks.type='sync'`），因此老的
> `/sync` 命令、`message_map` 映射表和已有数据库完全兼容，升级不需要迁移
> 数据，只自动补列。

---

## 1. 交互方式：按钮菜单（推荐）

`/start` 或 `/menu` 打开主菜单，全程点按钮：

```
🤖 TG 克隆助手
├─ 📥 新建克隆任务
│    ① 发源频道链接（或 @用户名）
│    ② 选目标：当前会话 / 发目标频道链接
│    ③ 选起点：从头 / 从指定消息 ID / 从指定时间 / 继续上次进度
│    ④ 选模式：复制 / 转发
│    ⑤ 确认 → 开始（默认跑完转持续监听）
├─ 👁 新建持续监听        （同一套向导，少了「起点」一步）
├─ 📋 克隆任务列表        （含已完成，记录永久保留；🛰 = 持续监听中）
├─ 📡 监听任务列表        （含克隆任务转来的持续监听，标注来源任务号）
├─ 💾 备份数据库
├─ ⚙️ 限流设置
└─ ❓ 命令与说明
```

向导状态保存在内存，15 分钟无操作自动失效；**已创建的任务不受影响**，
随时可从「克隆任务列表」继续。只有三类内容需要手打：源链接、消息 ID、时间。

### 命令速查

| 命令 | 作用 |
| --- | --- |
| `/kl <链接>` | 克隆该频道**全部**消息到本群，完成后自动持续监听 |
| `/kl 100-1100 <链接>` | 只克隆消息 ID 区间（**含两端**） |
| `/kljx <链接>` | 继续克隆：从上次游标补到最新，已克隆过的不重复 |
| `/kljx <链接> 120` | 从消息 120 开始继续克隆到最新（起点 ID 用 `/chaid` 获取） |
| `/kljx <链接> 120-1000` | 只克隆 msg 120~1000 |
| `/jt <链接>` | 只监听新消息，不补历史 |
| `/kllb` | 克隆任务列表（含已完成） |
| `/jtlb` | 监听任务列表 |
| `/chapd` | 转发一条频道消息到本群，识别频道名 / @用户名 / ID / 链接 |
| `/chaid` | 转发一条频道消息到本群，返回**消息 ID** 和**消息链接**（配 `/kljx` 用） |
| `/help` | 全部命令与功能对照 |

区间写法支持 `100-1100`、`100~1100`、`100—1100`、`100到1100`、`100至1100`；
区间/起始 ID 放在链接前后都可以（`parse_kljx_args` 会先抠出 ID，剩下的整段当链接；
要求 ID 前有空白，所以 `https://t.me/123456` 这种以数字结尾的链接不会被误认成 ID）。

`/kljx` 带 ID 时是**显式改写续跑点**：游标被设为 `ID-1`、`start_msg_id=ID`
（`set_clone_resume_point`），跳过「已是最新」判断，从那条消息开始重新克隆——
用于游标之后漏了消息、需要手动指定起点重补的场景。注意这段若克隆过会重复发送。

兼容旧用法仍然可用：

```
/clone [链接]                          # 等同于点「新建克隆任务」
/sync <链接> [--forward] [--from-id N] [--from-time 2024-01-31[T12:30]]
/syncrestrictedmsg <链接>
/monitor <链接> [--forward]            # 等价 /jt
/list
```

## 2. 克隆起点与终点

起点四种语义，终点默认是**源的最新一条**（正向 最早 → 最新）；用 `/kl A-B` 时终点
是消息 B：

| 起点 / 终点 | 菜单 | 命令 | 内部实现 |
| --- | --- | --- | --- |
| 从头开始 | ⏮ 从头开始 | 默认 | `offset_id=0` |
| 从指定消息 ID | 🔢 从指定消息 ID | `--from-id 1234` | `offset_id = 1234 - 1`（**含** 1234 这条） |
| 从指定时间 | 🕒 从指定时间 | `--from-time 2024-01-31` | 先按时间定位边界消息 ID，再 `offset_id=边界` |
| 继续上次 | ▶️ 继续上次进度 | 点任务里的「继续」/ `/kljx` | 用 `last_synced_msg_id` 作 `offset_id` |
| **到指定消息为止** | — | `/kl 100-1100 <链接>` | `end_msg_id=1100` → `max_id = 1101`（**含** 1100 这条） |

时间格式支持 `2024-01-31`、`2024-01-31 12:30`、`2024/01/31`、`20240131`、
`2024-01-31T12:30`、10 位 unix 时间戳。

> **续传优先**：只要任务的 `last_synced_msg_id > 0`，本次运行一律从游标继续，
> 起点设置不再生效 —— 避免「暂停后又把整个频道克隆一遍」。
> `/kljx` 还会把 `end_msg_id` 清零，否则补不到最新。

## 3. 进度记录

`tasks` 表一行就是一个任务，同时是它的进度快照：

| 列 | 含义 |
| --- | --- |
| `source_chat_id` / `source_topic_id` | 被克隆的源（含话题） |
| `target_chat_id` / `target_topic_id` | 接收目标 |
| `source_title` / `target_title` | 人类可读名称（菜单展示用，避免反复解析） |
| `start_msg_id` / `start_date` | 用户选择的起点（仅首次生效） |
| `last_synced_msg_id` | **克隆游标**：已处理到的源消息 ID |
| `total_count` | 待处理总量（服务端 `count`，非估算） |
| `done_count` / `fail_count` / `skip_count` | 成功 / 失败 / 跳过条数 |
| `notify_chat_id` / `notify_msg_id` | 进度消息位置（原地刷新，不刷屏） |
| `last_error` / `finished_at` | 最近错误 / 完成时间 |

`message_map` 逐条记录 `源消息 ID → 目标消息 ID`，可用于核对是否有重复或遗漏。

进度刷新：每成功转发 `clone.progress_notify_every` 条（默认 50）**编辑同一条
消息**：

```
📥 克隆任务 #12
进度: ▰▰▰▰▰▱▱▱▱▱  45.2%  (4,521/10,000)
游标: msg_id=48213 · 速率 1.2 条/秒
成功 4,500 · 失败 12 · 跳过 9
已用 1h02m · 剩余约 1h15m
```

## 4. 断点续传

三层保障：

1. **每处理完一个转发单元就落盘**（`last_synced_msg_id` + 计数，单行 UPDATE）。
   进程被 kill / 容器重启 / OOM 最多丢当前这一条，不会重头再来。
2. **手动暂停**：点「⏸ 暂停」→ 取消任务 → 状态 `paused`，游标保留。
3. **自动续传**：进程重启后，`status='running'` 的克隆任务会从游标继续
   （`clone.auto_resume: true`）。关掉则置为 `paused`，等手工点「继续」。

续传是**幂等**的：从 `last_synced_msg_id` 之后严格继续，不会重复发送已有内容。

---

## 5. 跑完之后：持续监听

克隆任务 `completed` 之后默认**不结束使命**：`syncer.on_complete` 会回调
`_on_clone_completed` → `_ensure_follow_monitor`，为同一个「源 → 目标」建一个
`monitor` 任务接管后续新消息，并通过 `parent_id` 反向指回克隆任务。

```
克隆任务 #12  completed   ──follow──▶  监听任务 #18  running
   🛰 持续监听: 开启（监听任务 #18）        （来自克隆任务 #12）
```

- **全局开关**：`clone.follow_after_finish: false` 可关掉这个自动行为；
- **单任务开关**：任务详情里的 `🛰 持续监听: 开启（监听任务 #N）` / `⏹ 关闭`，
  对应按钮 `follow:<id>`（`_toggle_follow`）；
- 关闭只是把对应监听任务置为 `paused` 并清掉 `follow` 标记，**记录与已转发计数都保留**，
  再点一次即恢复；

## 6. 记录永久保留

`completed` 不会再让任务从列表消失：

| 动作 | 效果 |
| --- | --- |
| 克隆跑到末尾 | `status='completed'`，仍在「克隆任务列表」里，带 ✅ 与完成时间 |
| 点「🗑 删除」 | `status='deleted'`（**软删除**），列表看不到，但游标 / `message_map` 仍在库里 |
| 误删想找回 | 直接把 `tasks.status` 改回 `paused`，任务立刻回到列表 |
| 想接着补新消息 | 详情页「🔁 继续补新消息」或 `/kljx <链接>` |
| `/kljx` 已无新消息 | 回复「已是最新」并保持 `completed`，不会空跑 |

列表排序为 `running → paused → failed → 其它（含 completed）`，
`get_tasks_for_list(db, CLONE_TASK_TYPES, 20)` 一次取 20 条。

## 7. 转发策略：私有频道不再下载

公共频道和私有频道走**同一套降级顺序**，只有上一层做不到才往下掉：

```
① Bot 直接克隆       Bot 原生转发 / drop_author 无痕转发 / 用 Bot 取到的媒体引用发送
        ↓ Bot 读不到源（典型：私有频道没把 Bot 拉进去）
② UserBot 转发       UserBot.forward_messages（copy 模式 drop_author=True）
        ↓ UserBot 不在目标 / 没有发帖权限
②b UserBot 读+Bot写  用 UserBot 取到的消息交给 Bot 发送（仍不下载）
        ↓ 源禁止转发 / 媒体引用失效 / Bot 也发不出去
③ 下载 + 上传        UserBot 下载到临时目录，Bot 重新上传
        ↓ 全部失败
④ #fail2forward     发一条带源链接的失败标记
```

**为什么私有频道原来慢**：Bot 不在私有频道里，策略①必然失败；原来的第二层是
「UserBot 读 + Bot 写」，而 Bot 拿 UserBot 取到的媒体引用去发送，私有源上常被判无效，
于是几乎每条都掉到第③层——下载再上传，速度完全由文件体积决定。

**现在**：只要 UserBot 在源频道里、并且是目标频道的管理员（有发帖权限），
第②层就能命中。`forward_messages` 是**服务端搬运**，字节不经过你的机器：

| | 下载+上传 | UserBot 转发 |
| --- | --- | --- |
| 1GB 视频耗时 | 取决于家宽上行，通常几分钟到几十分钟 | 一次 RPC，通常 < 1 秒 |
| 磁盘占用 | 需要一个文件的临时空间 | 无 |
| 单文件上限 | 受 Bot 上传上限（2GB/4GB）限制 | 不受上传上限影响（转发不是上传） |
| 画质 | 重新编码封装参数，可能丢流 | 原样搬运 |

**代价与注意**：

- **发帖人变了**：`copy` 模式在第①层是 Bot 发帖，在第②层是 **UserBot** 发帖
  （`drop_author` 只去掉「转发自」，发送者仍是 UserBot）。要求署名必须是 Bot 时，
  把 `transfer.userbot_forward` 设为 `false`；
- **UserBot 必须能读源**：`/jt`、`/kl` 建任务前已校验 UserBot 是否已加入源；
- **目标侧权限**：UserBot 需要在目标频道是管理员且有「发布消息」权限，否则自动落到②b；
- **风控**：UserBot 是用户账号，详见下一节。

### 能力缓存（提速的另一个大头）

「Bot 读不到这个源」「UserBot 发不进这个目标」判定一次就记住，有效期
`transfer.probe_ttl_seconds`（默认 1800 秒），期间不再重复触发注定失败的权限错误。
以前每条消息都要先撞一次 `ChannelPrivateError` / `ValueError`，几千条就是几千次
无效 RPC，既慢又难看（日志里一片"异常"）。

Bot 被重新拉进源频道后，最多等缓存过期（或重启进程）即可恢复第①层。

## 8. 风控：怎么把 UserBot 的风险压到最低

UserBot 走的是**用户账号**，被限流/限制的代价远高于 Bot（Bot 被限流只是慢，
用户账号被限制可能连群都发不了言，极端情况会被强制下线）。因此：

| 措施 | 默认值 | 说明 |
| --- | --- | --- |
| 独立节奏 | `userbot_forward_interval: [3, 6]` | 命中 UserBot 路径时**替换**通用 `forward_interval`，不叠加 |
| 批次长歇 | 每 25 条歇 `[60, 120]` 秒 | 用户账号最忌长时间匀速搬运 |
| FloodWait 缓冲 | `+5` 秒 | 官方要求等 N 秒，这里等 N+5，不贴红线 |
| 连续熔断 | `userbot_max_flood: 3` | 连续 3 次 FloodWait 后**本次运行停用**第②层，改走 Bot/下载；重启或换账号后恢复 |
| 尊重 noforwards | 自动 | 源开了「禁止转发」就不去试，避免反复被拒 |
| 去重 | `message_map` | 同一条消息不会因为重试被转两次（重复搬运是最典型的垃圾行为特征） |

**建议**：

1. **别把 UserBot 只当搬运工**——它同时在被克隆频道里，日常也有活动，属于"正常账号行为"；
2. **目标频道给 UserBot 管理员权限**，而不是让它用"转发到已保存"绕路；
3. **一次只跑一个克隆任务**，多个任务并发抢同一个 UserBot 是最容易触发限流的用法；
4. **想更保守**：`userbot_forward_interval: [8, 15]`、`userbot_forward_pause_every: 15`；
5. **完全不想动 UserBot**：`transfer.userbot_forward: false`，退回②b（Bot 发帖）→ ③。

**适用条件（第②层能命中的前提）**：

- UserBot 是源频道的成员（能读）；
- UserBot 是目标频道的管理员且有发帖权限；
- 源没有开启 `noforwards`（受限内容 Telegram 会直接拒绝转发，只能下载重传）；
- 目标不是「UserBot 被禁言/限制」的群。

## 9. 大频道不再撑爆内存

旧实现会先把整频道消息全读进内存再逐条转发，几万条就危险。现在按
`clone.batch_size`（默认 200）**流式分批**：

- 边拉边转，内存占用恒定；
- 相册不会被切到两批（`core.clone_plan.split_album_tail` 保证整组进入同一批），
  只有「单组图片数 > batch_size」这种极端情况才硬切；
- 服务消息与空消息（无文本无媒体）计入 `skip_count` 并推进游标，不会卡住。

## 10. 配置

```yaml
clone:
  auto_resume: true            # 重启后自动从断点继续
  batch_size: 200              # 每批拉取条数
  progress_notify_every: 50    # 每 N 条刷新一次进度
  max_concurrent: 1            # 同时最多跑几个克隆（其余排队）
  stall_alert_seconds: 600     # 多少秒无进展就告警（0=关闭）
  follow_after_finish: true    # 克隆跑完自动转持续监听

transfer:
  userbot_forward: true         # 允许 UserBot 直接转发（策略②）
  userbot_copy_fallback: true   # UserBot 进不了目标时退回「UserBot 读 + Bot 写」（策略②b）
  userbot_max_flood: 3          # 连续 N 次 UserBot FloodWait 后本次运行停用策略②
  userbot_flood_buffer: 5       # FloodWait 额外多等的秒数
  probe_ttl_seconds: 1800       # 「Bot 读不到源 / UserBot 不能发目标」判定缓存时长
  prefer_userbot_on_own_target: false  # 目标为自己频道时 UserBot 先行（默认关，见下）
  strategy_timeout: 1200        # 单条策略最长耗时，超时降级（0=不限）
  file_ref_retries: 2           # 媒体引用过期后的重取重试次数
  prefetch_ahead: 1             # 下载预取深度（0=关闭）

rate_limit:
  userbot_forward_interval: [3, 6]     # UserBot 每条的间隔（替换通用间隔）
  userbot_forward_pause_every: 25      # 每 N 条长歇
  userbot_forward_pause_time: [60, 120]
```

升级到本版本后首次启动会自动给 `tasks` 表补齐新增列（`PRAGMA table_info`
比对后 `ALTER TABLE ADD COLUMN`，只增不改，老数据保留），本轮新增
`end_msg_id`、`follow`、`follow_task_id`、`parent_id`。

数据库层面还有一次自动迁移：给 `message_map` 建 `UNIQUE(task_id, source_msg_id)`。
若旧库里已有重复映射（重跑造成），会先按该组合保留最早一条、删掉其余，再建索引；
整个过程幂等，日志里会出现 `已为 message_map 建立唯一索引（重复映射已清理）`。

## 11. 长任务会怎么失败，以及怎么兜住

克隆一个几千条的频道通常要跑几小时。实践中最常见的失败不是「慢」，而是下面三类
**静默失败**——表面上任务还在 running，实际上已经不再前进：

| 现象 | 根因 | 本项目的兜法 |
| --- | --- | --- |
| 进度条长时间停在同一游标 | 半开连接 / TCP 假死，Telethon 请求永久挂起 | `transfer.strategy_timeout`（默认 1200s）超时即放弃该策略继续降级；独立看门狗 `clone.stall_alert_seconds`（默认 600s）主动发消息告警 |
| 后半段媒体成批失败 | `file_reference` 过期（引用有时效，长任务必然遇到） | `_with_fresh_ref` 重取消息拿新引用再试，`transfer.file_ref_retries`（默认 2）次 |
| 目标频道出现重复消息 | 重跑 / 续补 / 超时重试把同一条又喂了一遍 | `message_map` 唯一索引 + 发送前 `get_mapped_ids` 批量查重，已映射计入 `skip_count` |

### 完整性校验

克隆结束的消息末尾会多出两行：

```
📊 完整性: 源 1,286 条 · 已映射 1,279 条 · 覆盖率 99.5% · 缺口 7 条（/klfail 查看，/retryfail 补）
• 自愈: 超时止损 2 次 · 引用刷新 1 次
```

- 分母是「源范围内应处理条数 − 跳过条数」（跳过的是服务消息/空消息，本就不该落地）；
- 缺口 > 0 时先 `/klfail <任务id>` 看原因，再 `/retryfail <任务id>` 补；
- 补发**不会改动续跑游标**，补完仍可正常 `/kljx` 跟新。

### 并发闸门为什么默认 1

每个 `Syncer` 自带一个 `RateLimiter`，两个任务并行时实际请求频率是配置值的 2 倍，
FloodWait 会成倍到来；而克隆本身是「服务端搬运」，并行并不提速（瓶颈在 Telegram 侧）。
所以默认排队，需要时再调 `clone.max_concurrent`。

### 关于 `prefer_userbot_on_own_target`

默认关闭。策略①（Bot 直接转发）本身就是服务端搬运、不占本机带宽，单条约 0.3s；
UserBot 有独立的 3–6s 节奏，把 UserBot 提前反而慢一个数量级。
只有当出现「Bot 能在源里读、却在目标里发不出（被限制/无发言权）」这种组合时，
打开它才能省掉每条一次的失败探测。

## 12. 常见问题

**Q：点了「继续」但没有任何反应？**
看日志有没有 `克隆任务 #N 已从游标 X 继续`。若源已不可读（UserBot 被踢、
频道转为私有），任务会标记 `failed` 并在 `last_error` 里写明原因，游标保留，
修好权限后可继续。

**Q：克隆完成了，但列表里还想看到它？**
能在。完成的任务状态是 `completed`，仍留在「克隆任务列表」；只有你点删除才会
以 `deleted` 软删除消失，数据仍在库里。

**Q：`/kljx` 会重复克隆吗？**
不带 ID 时不会：它按「源（含话题）→ 目标」找最新一条克隆记录，把状态改回
`running`（保留游标、清空 `end_msg_id`）后从 `last_synced_msg_id` 之后继续。
**带 ID 时会**：`/kljx <链接> 120` 是显式要求"从消息 120 重新克隆"，
从 120 到最新这段若克隆过就会重复发送——这是设计使然，用于漏消息后手动重补。

**Q：怎么知道某个频道该用哪个 ID？**
- 要**频道 ID / 链接**：`/chapd`，转发该频道任意一条消息，机器人回频道名、
  @用户名、ID 和可直接复制的 `/kl` / `/kljx` / `/jt` 命令。
- 要**某条消息的 ID**：`/chaid`，转发那条消息，机器人回它的消息 ID 和
  `t.me` 消息链接，并附上现成的 `/kljx <链接> <ID>` 命令。

**Q：目标频道收不到消息？**
先把 Bot 加为目标频道管理员（需要发消息权限）。菜单在选目标时会用
`bot.get_entity` 做一次可达性校验。

**Q：进度条百分比和源里显示的总数对不上？**
`total_count` 是服务端按「游标之后（并受 `end_msg_id` 上界限制）」统计的条数
（含服务消息），实际转发会略少，`skip_count` 会把这些差额显露出来。

**Q：能不能只克隆某个话题？**
可以。发带话题的链接（`https://t.me/c/123456/3/962`）即可，`source_topic_id`
会记录在任务里。

**Q：克隆到一半想改目标？**
不支持改已有任务的目标。建议删掉任务，用「继续上次进度」以外的方式新建一个
（游标是按任务记录的，新任务会从你选的起点开始）。

**Q：私有频道还是在下载，没走 UserBot 转发？**
按顺序查日志：
1. `策略2: ... 跳过（该目标已被判定 UserBot 无发言权）` → UserBot 不是目标管理员，或没有发帖权限；
2. `策略2: ... 跳过（源禁止转发(noforwards)）` → 源开了「禁止转发」，只能下载重传；
3. `跳过（transfer.userbot_forward=false）` → 配置里关掉了；
4. `UserBot FloodWait 已超 3 次` → 本次运行熔断，重启进程/换账号后恢复；
5. `无法解析源实体` → 该 UserBot 根本没加入源频道。

**Q：为什么目标频道里的帖子是 UserBot 发的，不是 Bot？**
这就是策略②的效果：`drop_author` 只去掉「转发自 X」，发送者仍是执行转发的账号。
要让 Bot 发帖，设 `transfer.userbot_forward: false`（会退回「UserBot 读 + Bot 写」，
私有源上仍可能落到下载重传）。

**Q：刚把 Bot 加进源频道了，为什么还走 UserBot？**
能力判定有缓存（`transfer.probe_ttl_seconds`，默认 30 分钟）。等缓存过期或重启进程即可。
