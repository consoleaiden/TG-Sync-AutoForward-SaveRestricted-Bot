# 实时监听任务

监听（`monitor`）与克隆（`sync`）共用 `tasks` 表，但语义不同：克隆有明确的终点，
监听只有一个「开始监听」的动作，之后按新消息持续转发。

克隆任务跑完后会**自动建一个监听任务**接管后续新消息（`clone.follow_after_finish`），
这类监听的 `parent_id` 指回来源克隆任务，列表里显示「（来自克隆任务 #N）」。

监听的转发走与克隆**同一套降级链**（Bot 直接 → UserBot 直接转发 → UserBot 读+Bot 写 →
下载上传，见 [clone.md 第 7 节](clone.md#7-转发策略私有频道不再下载)），
所以私有源的新消息同样不会触发下载，单条通常 1 秒内完成。

## 1. 创建

三个入口，效果一致（都走 `_create_monitor_task`）：

- **按钮**：`/start` → 「👁 新建持续监听」→ 发源链接 → 选目标 → 选模式 → 确认
- **命令**：`/jt <链接>`，或旧的 `/monitor <链接> [--forward]`
- **自动**：克隆任务完成时由 `syncer.on_complete` / `restricted_syncer.on_complete`
  → `_on_clone_completed` 触发。**不看 `follow` 标志**——克隆跑完一律建/恢复监听
  并置 `follow=1`，所以每个完成的克隆都会出现在监听任务列表里；
  想整体关掉用 `clone.follow_after_finish: false`。

监听列表每页 5 条，底部「◀ 上一页 / x/y 页 / 下一页 ▶」翻页；
命令侧 `/jtlb`、`/jtlb 2`。列表标题显示总监听数与运行中数量。

创建成功后会立刻发一条确认消息，包含任务编号、源、目标、模式、监听范围
（全部新消息 / 仅话题 #N）以及「详情 / 监听任务 / 暂停」按钮。**没有这条消息就说明没建成功**，
不必反复点确认；若失败，消息会原地改成错误原因 + 常见原因 + 「重试」按钮。

## 2. 任务记录了什么

| 字段 | 含义 |
| --- | --- |
| `source_chat_id` / `source_topic_id` | 监听的源频道与话题（话题 1 = General） |
| `target_chat_id` / `target_topic_id` | 转发目标 |
| `mode` | `copy`（不带来源标记）/ `forward` |
| `status` | `running` / `paused` / `failed` |
| `parent_id` | 由克隆任务转来时，指回克隆任务编号 |
| `follow` | 来源克隆任务那边记录的「持续监听」开关 |
| `done_count` | 已成功转发条数（相册按条计） |
| `fail_count` / `skip_count` | 转发失败 / 受限跳过 |
| `last_synced_msg_id` | 最近处理过的源消息 ID |
| `last_error` | 最近一次失败原因 |
| `updated_at` | 最近活动时间（UTC 存储，界面转本地时区显示） |

## 3. 进度怎么更新

监控是长期低频写入，**不做每条消息一次写库**：

- 单条转发 → 内存计数 +1
- 相册 → 整组统计，成功条数进 `done_count`，其余进 `fail_count`
- 受限跳过 → `skip_count` +1
- 每 5 秒批量落盘一次（`MONITOR_STATS_FLUSH_SECONDS` 可调）；暂停 / 删除 / 源不可访问时立即落盘

因此界面上的数字最多滞后 5 秒，进程被 kill 最多丢这 5 秒内的计数，不影响消息本身是否转发。

## 4. 事件是怎么收的（重要）

早期实现用 `events.NewMessage(chats=<源>)`，在 UserBot **无法解析该实体**时
（私有频道、会话刚重建、实体未缓存）会**静默收不到任何更新** —— 表现就是
「任务建好了、列表也在、但新消息永远不转发」。

现在改成注册 `events.NewMessage()` **全量接收**，再用 `_match_chat` 手工比对
`event.chat_id`（拿不到时退回 `message.peer_id`；两者都判断不了就**放行**，
宁可多判一次也不静默漏转）。这样即使实体没缓存，只要 Telethon 收到更新就能命中。

## 5. 在哪看

- 主菜单 →「📡 监听任务列表」或 `/jtlb`：列出全部运行中/暂停/失败的监听，
  每个显示源（含话题范围）、目标、已转发 / 失败 / 跳过、最近消息 ID、最近活动；
  由克隆任务转来的会标注「（来自克隆任务 #N）」
- 主菜单 →「📋 克隆任务列表」或 `/kllb`：克隆任务列表（含已完成），
  持续监听中的克隆带 `🛰` 标记
- `/list`：命令式混排列表，点进去同样是完整详情
- 详情页可「⏸ 暂停」/「▶️ 继续监控」/「🛰 持续监听」/「🔁 继续补新消息」/「🗑 删除」/「🔄 刷新」

## 6. 开关某个克隆的持续监听

任务详情里有 `🛰 持续监听: 开启（监听任务 #N）` / `⏹ 关闭`（回调 `follow:<id>`）：

- 开启 → 若已有对应监听就恢复它，没有就新建一个（`_ensure_follow_monitor`）
- 关闭 → 把对应监听置为 `paused` 并清 `follow` 标记，**记录和已转发计数都保留**，
  之后再点开启即可恢复，不用重建

## 7. 防重复

同一「源（含话题）→ 目标（含话题）」只允许一个运行中或暂停的监控任务：

- 菜单/`/jt` 再次创建 → 提示「相同的监听已存在：#N」，不新建；
  如果该任务处于暂停/失败，直接给「▶️ 继续监控」按钮
- `/monitor` 重复执行 → 回复已有任务编号，不新建

这样避免同一条新消息被注册两遍 handler、转发两遍。确实要重建时先删除旧任务。

## 8. 常见问题

**Q：暂停后再点「继续监控」，历史消息会补发吗？**
不会。监控只转发暂停期间之后的新消息；补历史请用克隆任务（`/kljx` 或「🔁 继续补新消息」）。

**Q：重启容器后监控还在吗？**
在。启动时 `restore_tasks()` 会把 `status=running` 的监控重新注册；`paused` 的保持暂停。

**Q：克隆跑完了，为什么群里还在继续收新消息？**
这是设计如此：克隆完成后自动转持续监听（`clone.follow_after_finish: true`）。
想停就在任务详情里点「⏹ 关闭」，克隆记录不会消失。

**Q：为什么已转发条数比群里看到的少？**
受限消息会被 `#fail2forward` 标记替代且计入 `skip_count`；相册里部分失败也按条计。

**Q：同一个源能同时转发到两个目标吗？**
可以，目标不同即视为不同任务；只有「源和目标都相同」才会被判重复。
